# Памятка для защиты

## Общая идея

«Перевод — одна PostgreSQL-транзакция. В ней мы захватываем ключ идемпотентности, блокируем счета, проверяем актуальный остаток, обновляем оба balance, пишем debit/credit и фиксируем конечный статус. База дополнительно проверяет ограничения и структуру двойной записи».

## SQL и ActiveRecord

1. Сверка: LEFT JOIN сохраняет счета без движений; COALESCE превращает пустую сумму в ноль. Начальные деньги тоже обязаны быть в ledger. На демо получаются расхождения 1100, 600, −200.
2. Net-аудит: сумма сторон перевода должна быть нулевой. Но пустой ledger, чужие счета, обратные знаки и неверные взаимно гасящие суммы тоже могут дать ноль. Поэтому есть структурный аудит: ровно два движения на нужных счетах и на точную сумму перевода.
3. Топ отправителей: только completed за 30 дней, GROUP BY user_id объединяет счета одного пользователя. Tie-break по user_id делает top-5 воспроизводимым.
4. Неактивность: NOT EXISTS ищет отсутствие свежих движений и включает никогда не использованные счета. AR NOT IN безопасен из-за NOT NULL account_id. Индекс account_id/created_at обслуживает проверку.

## Почему исходный код неверен

Нет общей транзакции: сбой может оставить только списание. Нет блокировки: два запроса проверяют один старый остаток. Ruby-арифметика по stale objects даёт lost update. Баланс при этом может оставаться неотрицательным, но ledger/зачисления уже окажутся неправильными. Нет ключа идемпотентности: retry после сетевого timeout списывает снова.

## Конкуренция

«Блокируем оба счёта по возрастанию id. Это предотвращает account-lock цикл у встречных A→B/B→A. FOR NO KEY UPDATE достаточен для balance и совместим с KEY SHARE, который берут проверки FK. Для такого check-and-debit достаточно READ COMMITTED вместе с явными locks».

Пессимистичные locks проще в этой короткой критической секции. Optimistic locking тоже возможен, но под hot-account нагрузкой увеличивает повторы. SERIALIZABLE не заменяет idempotency и требует обработки serialization failures. Общий порядок наших locks не исключает deadlocks с другими операциями системы, поэтому retry сохраняется.

## Идемпотентность

«Точка сериализации — unique index. INSERT ON CONFLICT ждёт незавершённую конкурирующую вставку: после её commit replay читает конечный результат; после rollback может выполнить перевод сам. Изменённые параметры с тем же key дают 409».

Failed из-за нехватки средств остаётся failed даже после пополнения. Новый бизнес-запрос требует нового key. Если процесс упал после commit, но до ответа, клиент повторяет прежний key и получает прежний transfer. В текущем решении ключи не удаляются; TTL изменил бы контракт защиты от поздних replay.

## Деньги и входной контракт

BigDecimal/NUMERIC сохраняют десятичную арифметику. Float отвергается. NUMERIC(18,2) сам по себе может округлить 1.001, поэтому scale проверяется до записи. NaN/Infinity отвергаются сервисом, NaN — также CHECK в БД. Максимальная сумма — 9999999999999999.99; получатель с недостаточной числовой ёмкостью даёт стабильный failed/balance_limit_exceeded.

ID строго целочисленный и входит в bigint. Ключ — строка до 255 символов. Обязательные поля проверяются до вызова сервиса. Сервис нельзя вызывать во внешней транзакции: это программно проверяется, потому что retry должен владеть внешним rollback boundary.

## Ошибки

Повторяются только deadlock, serialization failure и lock timeout: три попытки целой транзакции, backoff с jitter. Не повторяются ошибки ввода, conflict и недостаток денег. При техническом сбое rollback удаляет и захваченный key, и изменения balances. После исчерпания transient retry API даёт 503 с Retry-After; повторять нужно тем же key.

## Инварианты БД

CHECK — неотрицательный balance, положительная сумма, разные счета, допустимые status/reason, kind и конечные числовые значения. FK/NOT NULL — ссылки и обязательность. UNIQUE — один key и одна сторона перевода на счёт. Ledger нельзя менять или удалять. Transfer identity/terminal result неизменяемы; DELETE transfer запрещён, чтобы не потерять key.

Deferred constraint trigger проверяет completed/failed на COMMIT, когда обе записи уже должны существовать. Обычный immediate trigger отвергал бы промежуточную первую сторону двойной записи. Pending разрешён схемой, но синхронный сервис его не коммитит.

Равенство balance и SUM(ledger) не гарантируется простым CHECK: оно обеспечивается транзакционным writer и сверкой. Прямой неотрицательный UPDATE balance в обход writer всё ещё может нарушить эту связь. Runtime DB role не должен иметь DDL/TRUNCATE/disable-trigger права; owner/superuser может обойти обычную защиту.

## Что доказывают тесты

20 одновременных списаний по 10 со 100 должны дать ровно 10 completed/10 failed. Проверяем не только balance >=0, но и сохранение общей суммы, две стороны каждого успеха и сверку каждого счёта. Отдельно один key из многих потоков, встречные переводы и 50 команд на 5 счетах.

Workers используют отдельные PostgreSQL connections и стартовый barrier. Транзакционные fixtures выключены: setup должен быть закоммичен и виден другим соединениям. Все workers завершаются до TRUNCATE даже при ошибке. Нужны достаточные pool/max_connections.

`bin/prove-race` подставляет исходный read/check/write с дополнительным барьером после чтения. Он детерминированно проводит 20 операций вместо 10; та же проверка падает именно на денежном инварианте. Рабочий сервис не загружает этот adapter. `bin/stress` повторяет нормальные сценарии 20 раз.

## Масштабирование и аудит

10k tps = 864 млн transfers и 1,728 млрд ledger rows в сутки. Это расчёт объёма, а не результат benchmark. Locks горячего счёта, WAL/commit, connections и индексы ограничат масштабирование. При удержании одной строки 2 ms порядок её предела — 500 операций/s; дополнительные Rails processes не сокращают критическую секцию.

Начинаем с измерений и коротких transactions, pool/admission control, затем отделяем аналитику, вводим partitions/архив. Sender queue не устраняет конфликт общего receiver. Cross-shard saga — durable state machine с reservations/outbox/inbox; это иной контракт, чем мгновенный ACID-перевод одной БД.

Time partitioning конфликтует с глобальным UNIQUE(key) без partition key: нужен отдельный registry. Sequence id не задаёт commit order: MAX(id) без протокола watermark может пропустить поздний commit меньшего id. Snapshots/CDC должны иметь согласованную границу.

Один SELECT уже видит согласованный MVCC snapshot. REPEATABLE READ нужен для серии запросов сверки. Нельзя сравнивать balance с primary и ledger с отстающей replica. Расхождение — инцидент; исправление оформляется новой обратной операцией после расследования, а не переписыванием истории.
