# Часть 2: code review и исправление

## Существенные дефекты исходного варианта

1. **Нет транзакции.** Исключение после списания, но до зачисления/ledger, оставляет частично проведённую операцию.
2. **Check-then-act по stale object.** Два запроса видят один остаток и оба проходят `from.balance < amount`.
3. **Lost update.** `from.balance - amount` вычисляется в Ruby из старого значения; поздний UPDATE может затереть ранний.
4. **Нет блокировок и общего порядка их получения.** Простое добавление locks в направлении transfer создаст deadlock для A→B и B→A.
5. **Нет идемпотентности.** Таймаут после commit, но до HTTP response, превращает безопасный client retry в двойное списание.
6. **Нет валидации суммы и пары счетов.** Ноль бессмысленен, отрицательная сумма инвертирует поток, self-transfer нарушает семантику.
7. **Строковое исключение.** `RuntimeError` не позволяет API отличить business rejection от infrastructure failure.
8. **Непредсказуемый status.** Сбой оставляет `pending`, а failure не имеет стабильного результата для replay.
9. **Нет DB constraints.** Обход ActiveRecord validation позволяет записать овердрафт, неверный status или дубликат ключа.
10. **Неверный return contract.** Последний `update!` возвращает `true`, а не transfer/result.
11. **Нет защиты ledger.** Движения можно изменить или удалить задним числом.
12. **Деньги не нормализованы.** Не отвергаются Float, лишняя scale и переполнение `NUMERIC(18,2)`.

## Исправление

`TransferMoney` принимает ids, decimal/BigDecimal и ключ. Это исключает доверие к загруженному ранее Account. Он сначала валидирует чистый input, затем в одной PostgreSQL transaction:

- делает `INSERT ... ON CONFLICT DO NOTHING` для ключа;
- при conflict сравнивает все семантические параметры и возвращает terminal result либо `IdempotencyConflict`;
- блокирует оба счета в едином порядке `id` через `FOR NO KEY UPDATE`;
- проверяет средства под lock;
- выполняет SQL arithmetic, пишет две ledger rows и terminal status;
- коммитит всё вместе либо откатывает всё.

`FOR NO KEY UPDATE` достаточно для изменения неключевого `balance` и совместимо с `FOR KEY SHARE`, который PostgreSQL использует при проверке FK. Более сильный `FOR UPDATE` увеличивает ненужные конфликты с FK. Единый порядок резко снижает deadlocks, но retry всё равно нужен: в системе могут быть другие lock graphs.

Unique index, а не `SELECT` перед `INSERT`, является точкой сериализации idempotency. Если первый процесс упал до commit, его transaction и ключ откатились, и ожидающий запрос сможет выполнить перевод. Если процесс упал после commit, replay получает уже сохранённый terminal result.

Retry ограничен deadlock, serialization failure и lock timeout; validation, недостаток средств, conflict ключа и integrity errors не повторяются. Backoff с jitter ограничивает синхронные повторные столкновения. После трёх попыток API возвращает 503, а клиент повторяет тот же key.

Входной контракт проверяет обязательные HTTP-поля, целочисленность и bigint range IDs, тип ключа и точную scale суммы. Переполнение баланса получателя является стабильным failed/balance_limit_exceeded. Внешняя транзакция программно отвергается до записи. Ledger/transfer защищены от NaN и изменения сохранённого terminal result; DELETE transfer запрещён для сохранения ключей.

## Почему недостаток средств — `failed`

Это осознанная семантика idempotency: исход попытки фиксируется навсегда. Если на счёт позже пришли деньги, replay старого ключа всё равно вернёт `failed`; для новой бизнес-попытки нужен новый key. Альтернатива — откатывать transfer и допускать изменение результата replay — хуже для предсказуемости платежного API.
