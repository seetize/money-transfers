# Часть 1: SQL и ActiveRecord

Исполняемые варианты находятся в `sql/`, ActiveRecord-эквиваленты — в `app/queries/`, проверки — в `spec/queries/financial_queries_spec.rb`.

## 1. Расхождение баланса и ledger

`01_balance_mismatches.sql` использует `LEFT JOIN`, поэтому сохраняет счета без движений, а `COALESCE(..., 0)` трактует их ledger balance как ноль. На данных задания возвращаются все счета:

| account_id | balance | ledger_balance | difference |
| ---: | ---: | ---: | ---: |
| 1 | 1000.00 | -100.00 | 1100.00 |
| 2 | 500.00 | -100.00 | 600.00 |
| 3 | 0.00 | 200.00 | -200.00 |

Индекс `(account_id, created_at)` полезен для инкрементальной/периодной сверки. Полная агрегация всей истории всё равно читает ledger целиком; на больших объёмах используются snapshots.

## 2. Ненулевая сумма движений

`02_unbalanced_transfers.sql` на demo data возвращает пустой набор. Это не означает, что данные корректны: failed transfer 3 не имеет движений, что допустимо, а completed 1 и 2 имеют нулевой net.

Одной проверки `SUM(amount) = 0` недостаточно. Она пропускает completed без записей, `-50/+50` при `transfer.amount = 100`, записи на чужих счетах, обратные знаки, лишние взаимно гасящие пары и движения у failed/pending. Поэтому `05_invalid_transfer_ledgers.sql` дополнительно проверяет число, владельца, знак и сумму каждой стороны. Тот же структурный инвариант для terminal status проверяет deferred trigger на коммите.

## 3. Топ-5 отправителей за 30 дней

`03_top_senders.sql` агрегирует по `accounts.user_id`, а не по счёту: у пользователя может быть несколько счетов. Учитываются только `completed`; вторичная сортировка по `user_id` делает результат детерминированным при равных суммах. Индекс `(from_account_id, created_at)` помогает по отправителю, но для глобального 30-дневного отчёта в production нужен также partial/time-oriented index либо аналитическая реплика.

Seed задаёт successful transfers 10 и 5 дней назад: результат user 102 → 200.00, user 101 → 100.00. Failed на 50.00 не учитывается.

## 4. Счета без движений за 90 дней

`04_dormant_accounts.sql` использует correlated `NOT EXISTS` и включает счета, у которых движений не было никогда. Индекс `(account_id, created_at)` обслуживает anti-join. ActiveRecord-вариант использует `NOT IN (subquery)`; он безопасен, потому что `ledger_entries.account_id NOT NULL`.

На demo все три счета имеют свежие движения: результат пустой. Отдельные тесты проверяют пустой счёт и точную 90-дневную границу.

Границы времени вычисляются базой в SQL и передаются параметром в query objects/testах, чтобы бизнес-запрос можно было воспроизводимо тестировать.
